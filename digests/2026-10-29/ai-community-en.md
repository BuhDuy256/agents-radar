The author cut input tokens on a BI agent that spent about 17,070 tokens on instructions and 36 tool declarations before any question, and 286,522 input tokens across ten model calls in a three-question offline replay. ### Tool descriptions that tell an agent when not to call the tool
The author explains that an agent chooses tools only from a tool's name, description and input schema — it never sees the code — and argues most tool descriptions are written too casually. For a made-up bike rental, he contrasts a weak `book` tool with `rental_book_bike`, whose four sentences state what it does, a 14-day limit, when to use it only after user confirmation, that the bike ID must come from `rental_search_bikes`, and that the same `requestKey` never books twice. Parameter descriptions and error messages that point to a fix are part of the design. Use this when agents call the wrong tool or pass invented IDs.

### Reversing prompt field order dropped a frozen policy from 85.0% to 19.2%
A new paper by Jian Mu, Ruibo Shen and Yao Shu (arXiv:2610.37255) argues that frozen-model harness comparisons mix two things: the harness's ceiling and the mismatch penalty of a policy post-trained on a different harness. On MiniWoB++, reversing the observation-field order, with all actions still valid, collapsed a frozen policy from 85.0% to 19.2%. On Terminal-Bench Lite, five coding harnesses ranked the same by accuracy as by estimated ceiling-minus-mismatch. The authors' recommendation: adapt checkpoints per harness or estimate the ceiling separately. The evidence rests on these tested setups, not on every harness.
