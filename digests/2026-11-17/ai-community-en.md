## Workflows
### Non-engineers assigned agents 40 merged pull requests in 60 days
Product managers, designers and support staff assigned small engineering tasks to coding agents and got pull requests back for review. According to epilot, 11 non-engineers shipped 40 merged PRs in 60 days, covering translations, UX fixes and small features. In this setup, an engineer configures the agents and their repositories once; requests arrive as plain-language tasks (from a board, Slack, Jira or GitHub, optionally with a triage step); a non-engineer assigns the task to an agent; an engineer reviews the resulting PR before merge. A companion workflow article describes the same pattern in Sharkly, framing the main skill as writing a task that states the problem, the definition of done, the location, evidence and what not to touch. Applicable when a team already has CI and review in place.

### A merge gate caught 17 type errors after an agent reported green tests
The author's team runs Claude Code engineer agents, a manager agent that is the only merger, and Codex reviewers in a shared agent-chat room. The manager re-runs CI's own verify script before merging, so it found 17 type errors in a PR whose `npm test` had passed. It also runs `git merge-tree` on every PR pair, verifies the combined tree on CI's image, and sets landing order so migration numbers follow it. Limit: a batch still went red after merging, on a UI timing bug, so the gate does not replace the pipeline after it.

### Author ran Kiro CLI as implementer behind five fixed tools for a month
The author wanted a planning AI to prepare requests while Kiro CLI did the implementation, without handing write credentials to the planner. He built BRIDGE: an MCP server plus controller where the chat-side AI holds no GitHub token or Kiro API key and can call only five tools (two read, three write). Repository, base branch and merge method are fixed server-side; Kiro runs headless on the write path; merge happens only if the specified HEAD SHA matches. He used ChatGPT as the chat client for about a month. Limits: this is his own environment, not an AWS-recommended configuration, and correctness of changes was left to AI review.

## Experiments and comparisons
### Self-checking builder stopped at status 200; separate judge reached 201
DevOps Daily scripted a plan/build/judge loop for one task: add a signup endpoint that hashes the password and returns 201. With a separate judge, the run took three loops — the judge rejected plain-text passwords, then rejected the 200 status because tests were green but the spec was not met, then approved 201. With the judge off, the builder graded itself and stopped after two loops with the wrong status. Limits: the simulator is scripted, not a live run, and its token counts (91k versus 56k) are authored values, not measurements. The companion Python toy shows a loop stops exactly where its definition of done allows.

### A completed tool span passed a trace contract while the tool reported failure
The author used a synthetic fixture against pinned versions `agent-inspect@6.31.35` and `@agent-inspect/mcp@6.31.35` to separate three signals: a promise resolving, an MCP result carrying `isError: true`, and the intended outcome actually happening. In the test, the wrapper preserved the returned result rather than throwing, and a completion-only trace contract passed while the same contract with `observations: { failOn: ["failed"] }` failed. Limits: this is a fixture, not a real MCP server or a production incident; TraceContract is a beta surface. He warns against treating `isError` as a retry classification.
